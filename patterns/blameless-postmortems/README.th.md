## ปัญหา

หลัง outage เรื่องที่เล่าง่ายที่สุดคือมีคนทำพลาด manager ถามว่าใครเป็นคน push deploy แล้ว report ก็ระบุว่าเป็น *human error* และ action item ข้อเดียวก็บอกว่า *ระวังให้มากขึ้น* ฟังดูเหมือนปิดเรื่องได้ แต่องค์กรแทบไม่ได้เรียนรู้อะไรเลย วิศวกรที่ merge change นั้นรู้ว่าเกิดอะไรขึ้นมากกว่าใคร และพอเขาถูกโทษ ทั้งเขาและทุกคนที่ดูอยู่ก็เรียนรู้ที่จะพูดน้อยลง: ความผิดพลาดไม่ถูกรายงาน, deploy ที่ดูเสี่ยงถูกเลื่อนออกไปและถูกรวมเป็นก้อนใหญ่ขึ้น และ incident report ก็ตัดรายละเอียดที่น่าอึดอัดทิ้ง เงื่อนไขที่ทำให้พลาดได้ง่าย (ค่า default ของ library ที่ไม่มีใครเช็ก, canary ที่ดู signal ผิดตัว, runbook ที่ขาดไปหนึ่งขั้น) ก็ยังอยู่ที่เดิม แล้วทีมถัดไปก็เดินเข้าไปเจอความล้มเหลวแบบเดียวกัน

นี่คือสิ่งที่เกิดในขั้นแรกของ diagram ที่ Acme Shop ในวันเสาร์ที่ 3 ตุลาคม 2026 ตัว checkout release 1.43.0 upgrade payment client library และค่า default timeout ของ library นี้เปลี่ยนจาก 3 s เป็น 30 s พอ payment provider ช้าลงในคืนนั้น thread ของ request ใน checkout ก็รอนานถึง 30 s ต่อตัวจนกองพะเนิน และ request ของ checkout ก็ fail ไปราว 27 นาที ส่วน review แบบโทษคนก็ชี้ตัววิศวกรที่ merge release เปิด action เดียวที่ไม่มีเจ้าของและไม่มีวันที่ และแชร์ report ให้คนแค่สามคน หกสัปดาห์ต่อมา call ของทีม delivery ที่ไปหา carrier API ก็ค้างเพราะค่า default 30 วินาทีของ library แบบเดียวกัน

## ทำงานยังไง

**postmortem** คือบันทึกที่เขียนไว้ของ incident หนึ่ง: ผลกระทบ สิ่งที่ทำเพื่อ mitigate และ resolve มัน ทำไมมันถึงเกิด และงานที่ต้องทำต่อเพื่อให้มันเกิดซ้ำได้ยากขึ้น บทที่ 15 ของหนังสือ *Site Reliability Engineering* ของ Google (*Postmortem Culture: Learning from Failure* โดย John Lunney และ Sue Lueder) วางมันไว้เป็นโอกาสเรียนรู้ของทั้งบริษัท และบอกชัดว่าไม่ใช่การลงโทษ แล้วก็ทำให้มัน **blameless**: การเขียนตั้งอยู่บนสมมติฐานว่าคนที่เกี่ยวข้องตั้งใจดี และตัดสินใจอย่างสมเหตุสมผลจากสิ่งที่รู้ในตอนนั้น และมองหาสิ่งที่ต้องเปลี่ยนในระบบและ process แทนที่จะหาว่าต้องแก้ที่ตัวคนไหน บทนี้สืบย้อนแนวคิดนี้ไปถึงวงการสาธารณสุขและการบิน ที่ความผิดพลาดอาจถึงชีวิต และความผิดพลาดแต่ละครั้งถูกมองเป็นโอกาสทำให้ระบบปลอดภัยขึ้น

บทความปี 2012 ของ John Allspaw ชื่อ *Blameless PostMortems and a Just Culture* ที่เล่าถึงการทำแบบนี้ที่ Etsy อธิบายว่าทำไมมันถึงได้ผล วิศวกรที่ไม่กลัวถูกลงโทษจะเล่าได้อย่างละเอียดว่าเขาทำอะไรไปและเมื่อไร เห็นอะไร คาดหวังและสันนิษฐานอะไร และเข้าใจ timeline ยังไงระหว่างที่มันกำลังเกิด คำบอกเล่านั้นคือข้อมูลที่องค์กรต้องการ และคนที่รู้สึกปลอดภัยพอจะเล่ามักกลายเป็นคนที่สอนคนอื่น ๆ ว่าจะเลี่ยงกับดักเดียวกันได้ยังไง Allspaw อ้างอิงนักวิจัยด้าน safety อย่าง Sidney Dekker และ Erik Hollnagel และหนังสือ *Behind Human Error* และเรียกเป้าหมายนี้ว่า **just culture**: วัฒนธรรมที่สมดุลระหว่าง safety กับ accountability

### ตัว document

### เขียนถึงการตัดสินใจของคน

ส่วนที่ยากของ blameless postmortem คือการเขียน พอมองย้อนหลัง ทางที่ถูกก็ดูชัดเจนไปหมด และคำอย่าง *ควรจะ*, *ไม่ได้ทำ* หรือ *ไม่ได้เช็ก* ก็ตัดสินคนด้วยความรู้ที่เขาไม่มีในตอนนั้น *The Field Guide to Understanding 'Human Error'* ของ Dekker (ฉบับที่ 3, 2014) เป็นคู่มือภาคปฏิบัติสำหรับเลี่ยงเรื่องนี้ มันเทียบมุมมองแบบเก่า ที่มองว่าคนไม่น่าไว้ใจไม่กี่คน ("bad apples") ทำให้ระบบที่ปกติปลอดภัยพัง กับมุมมองแบบใหม่ที่ถือว่าความผิดพลาดของคนเป็นจุดเริ่มต้นของการสืบสวนระบบ และมันเตือนเรื่อง hindsight bias กับการให้เหตุผลแบบ "เขาควรจะ" ที่สมมติถึงสิ่งที่ไม่ได้เกิดขึ้น (counterfactual) คำถามที่ต้องตอบสำหรับแต่ละการกระทำคือ ทำไมมันถึงดูสมเหตุสมผลสำหรับคนคนนั้นในตอนนั้น จากสิ่งที่เขารู้ สิ่งที่เขาพยายามทำ และสิ่งที่เขากำลังสนใจอยู่ นักวิจัยด้าน safety เรียกสิ่งนี้ว่า local rationality

ในทางปฏิบัติ แปลว่าให้เขียนถึงข้อมูลและระบบ แทนที่จะเขียนถึงตัวคน:

| แทนที่จะเขียนว่า | ให้เขียนว่า |
|---|---|
| วิศวกร push release ที่เสีย | release 1.43.0 upgrade payment client library ทำให้ default timeout เปลี่ยนจาก 3 s เป็น 30 s ตัว checkout พึ่งค่า default ทำให้โค้ดของ checkout เองไม่มี timeout ที่เปลี่ยนให้เห็น |
| canary ควรจะจับได้ | canary analysis เทียบ error rate และ p95 latency ของเส้นทางหลัก ส่วน payment latency ไม่ได้อยู่ใน signal ของมัน ทำให้ 1.43.0 ผ่าน |
| on-call หา fallback ได้ช้า | flag `payments.fallback` มีอยู่แต่ไม่อยู่ใน runbook ตัว rollback เริ่มตอน 20:24 แล้ว flag ก็เปิดตอน 20:31 |

### Review และแชร์

หนังสือ SRE แนะนำให้แชร์ draft และให้ senior engineer review ว่าครบถ้วนไหม: เก็บข้อมูลสำคัญมาแล้วหรือยัง การประเมินผลกระทบครบไหม การวิเคราะห์ลงลึกพอไหม action item เหมาะสมและเปิดไว้ใน priority ที่ถูกหรือเปล่า และผลลัพธ์ไปถึงคนที่ต้องรู้แล้วหรือยัง postmortem ที่ review แล้วจะเข้าไปอยู่ใน repository ที่ทีมอื่นค้นได้ บทที่ 10 ของ *The Site Reliability Workbook* เทียบ postmortem ฉบับแย่กับฉบับดีของ outage เดียวกัน ฉบับแย่ขาด context และตัวเลขสำคัญ ชี้นิ้วโทษด้วยภาษาที่ใช้อารมณ์ ระบุเจ้าของ document ไว้สี่คน แต่ action item ส่วนใหญ่ไม่มีเจ้าของที่ชัดเจน เปิด tracking bug ให้แค่ข้อเดียว แชร์แค่ในทีม และออกมาช้าไปสี่เดือน ตอนนั้น incident ก็เกิดซ้ำไปแล้ว บทนี้ยังยกกฎของ Ben Treynor Sloss ที่ Google ว่า postmortem ของ outage ที่กระทบ user ต้องมี bug ระดับ P0 หรือ P1 แนบอยู่อย่างน้อยหนึ่งตัว

เพื่อกระจายบทเรียน หนังสือ SRE เล่าถึง *postmortem of the month* ที่ส่งให้ทั้งองค์กร, ชมรมอ่าน postmortem ที่ทีมมาไล่ดู incident เก่าด้วยกัน และ Wheel of Misfortune ที่วิศวกรใหม่เล่น postmortem ในอดีตซ้ำเป็นเกมสวมบทบาท

## ลงมือทำจริงยังไง

1. **ตัดสิน trigger ไว้ก่อน incident ครั้งหน้า** ตัวอย่างในหนังสือ SRE เป็นรายการเริ่มต้นที่ดี: downtime หรือการทำงานที่แย่ลงที่ user เห็นเกิน threshold, ข้อมูลหายแบบไหนก็ตาม, on-call ต้องเข้าไปแทรก เช่น rollback หรือเปลี่ยนเส้นทาง traffic, เวลา resolve เกิน threshold หรือ monitoring ล้มเหลวจนคนต้องเจอ incident เอง ให้ใครก็ขอ postmortem ได้ และรวม near miss ด้วย ส่วน handbook ของ Atlassian ถ้าจะเทียบ บังคับให้ทำสำหรับ incident severity 1 และ 2 และให้เป็นทางเลือกสำหรับระดับที่ต่ำกว่า
2. **ให้มีเจ้าของและ deadline** กฎของ Acme คือต้องมี draft ภายในห้าวันทำการ เขียนโดยคนที่เกี่ยวข้อง (ในที่นี้คือ Mai, Tom และ Ploy) ตอนที่ยังจำได้ดี ที่ Atlassian ทีมเจ้าของ service ที่มีปัญหาจะเลือก postmortem owner ที่จะพามันผ่าน review และการอนุมัติ
3. **สร้าง timeline ขึ้นใหม่จากหลักฐาน**: incident doc ที่ scribe จด, log ของ channel (`#inc-checkout-1003`), กราฟ, deploy log และ audit log โดยที่ timeline แยกสิ่งที่คนรู้ในแต่ละช่วงออกจากสิ่งที่ทุกคนรู้ตอนนี้
4. **จัด review ที่มี facilitator** คนที่ไม่ได้เกี่ยวข้องกับ incident (ที่ Acme คือคนจากกลุ่ม SRE) ทำหน้าที่ facilitator ย้ำว่า review นี้ blameless ไล่ดู timeline รวบรวม contributing factor และถามคำถามปลายเปิด ส่วน agenda ที่ Atlassian แนะนำก็เรียงแบบเดียวกัน: ย้ำทุกคนว่าทำไม review นี้ถึง blameless ยืนยัน timeline ยืนยันสาเหตุ แล้วค่อยคิด action
5. **เปลี่ยนสิ่งที่พบให้เป็นงานที่ติดตามได้** action item แต่ละข้อมีเจ้าของหนึ่งคน วันครบกำหนด และ priority และอยู่ใน backlog ของทีมเจ้าของ (Jira, GitHub Issues หรืออะไรก็ตามที่ทีมใช้วางแผนงาน) ไม่ใช่อยู่แค่ใน document ติดตามด้วยว่าเสร็จหรือยัง: Atlassian ตั้งเป้าให้ "priority actions" ของตัวเองเสร็จในสี่หรือแปดสัปดาห์ตามแต่ละ service พร้อมการเตือนและ report ส่วน Acme ทำเสร็จ 3 จาก 4 ข้อภายใน 21 ตุลาคม และข้อที่สี่ก็เป็นไปตามกำหนด
6. **เผยแพร่ในที่ที่คนดู** repository ที่ค้นได้ (wiki space, Markdown file ใน Git หรือ feature postmortem ของ incident tool) พร้อม tag ที่สม่ำเสมอสำหรับ service, severity และ contributing factor ทำให้ค้นคำว่า *timeout* แล้วเจอ incident นี้ และทำให้มีคนเห็น trend ข้าม incident ได้
7. **แก้ทั้งประเภทของปัญหา ไม่ใช่แค่ครั้งนี้** ทีม platform ของ Acme ทำให้ timeout ที่ตั้งไว้ชัดเจนเป็นส่วนหนึ่งของ shared client library จะได้ไม่มีทีมไหนรับค่า default 30 วินาทีของ library มาอีก
8. **รักษานิสัยไว้**: postmortem of the month, กลุ่มอ่าน postmortem, incident เก่าที่เอามาเล่นซ้ำเป็น game day และหัวหน้าที่ใช้ภาษาแบบ blameless เอง และให้รางวัลอย่างเห็นได้ชัดกับคนที่เขียน postmortem และปิด action item ของมัน

## อยู่ตรงไหนใน solution

- **[Incident Management](../incident-management/)** ครอบคลุมเหตุการณ์เดียวกันระหว่างที่มันเกิด: การประกาศ SEV-2 บทบาทต่าง ๆ (Mai เป็น incident commander, Tom เป็น operations lead, Ploy ดูการสื่อสาร และมี scribe) และ incident doc ที่ timeline ของหน้านี้สร้างขึ้นใหม่จากมัน ส่วน postmortem คือจุดที่การรับมือจบ และการเรียนรู้เริ่ม
- **[SLOs and Error Budgets](../slo-error-budgets/)** นิยามว่าอะไรนับเป็นผลกระทบที่ user เห็น และ alert ตาม burn rate ที่ page หา Mai ก็สร้างอยู่บนมัน และ SLO ที่หลุดหรือ budget ที่ถูกเผาไปเยอะก็เป็น trigger ของ postmortem ที่เจอบ่อย ส่วน contributing factor ข้อที่สี่ คือ alert window 5 นาที เป็นคำถามเกี่ยวกับ alerting rule พวกนั้น
- **[Canary Release](../canary-release/)** และ **[Feature Flags](../feature-flags/)** โผล่ทั้งใน contributing factor และในสิ่งที่ไปได้ดี: canary analysis ดู signal ผิดตัว และ flag `payments.fallback` ทำให้ outage สั้นลง ส่วน action item หลักใช้ **[Timeout & Fallback](../timeout-and-fallback/)** พร้อม retry budget ตามที่อธิบายไว้ใน **[Retry with Backoff](../retry-with-backoff/)**
- **[Chaos Engineering](../chaos-engineering/)** เช็กว่าการแก้ใช้ได้จริง: game day ที่ตั้งใจทำให้ payment provider ช้าลง จะบอกว่า timeout ใหม่และ fallback ทำงานตามแผนหรือเปล่า
- **[The Three Ways](../three-ways/)** จัด postmortem ไว้ใต้ Third Way คือการเรียนรู้อย่างต่อเนื่อง และ **[You Build It, You Run It](../you-build-it-you-run-it/)** ทำให้ทีมที่เป็นเจ้าของ service เป็นทีมที่เขียน postmortem ของมันและลงมือทำ action ส่วน **[DORA Metrics](../dora-metrics/)** อย่าง change fail rate และ failed deployment recovery time บอกได้ในระยะหลายเดือนว่าการตามงานต่อได้ผลไหม

## ใช้ตอนไหนดี

postmortem คุ้มในทุกที่ที่ incident กระทบ user หรือวนกลับมา: ทุกทีมที่รัน production service และโดยเฉพาะองค์กรที่หลายทีมใช้ platform และ library ร่วมกัน เพราะบทเรียนของทีมหนึ่งช่วยปกป้องทีมอื่นได้ มันต้นทุนต่ำที่สุดเมื่อทำจนเป็นนิสัยที่รวม near miss ด้วย: near miss ที่ review ในครึ่งชั่วโมง มักแสดงจุดอ่อนแบบเดียวกับ outage ใหญ่ ด้วยต้นทุนแค่เศษเสี้ยว

ปรับวิธีทำให้เข้ากับตัวเอง แทนที่จะลอก process ของบริษัทใหญ่มาทั้งหมด:

- **ทีมเล็ก** ใช้ template หน้าเดียว และคุยกัน 30 นาทีก็พอ ตัว section และน้ำเสียงแบบ blameless สำคัญกว่าพิธีการ
- **อุตสาหกรรมที่มี regulation** อาจต้องส่ง incident report แบบทางการให้หน่วยงานกำกับหรือลูกค้า และ report นั้นก็มีกฎของมันเองเรื่องถ้อยคำ การ review ด้านกฎหมาย และการเปิดเผยข้อมูล ให้แยก document สำหรับเรียนรู้ภายในออกจากมัน และตกลงกับฝ่ายกฎหมายว่า document ภายในใส่อะไรได้บ้าง
- **การตั้งใจทำร้ายเป็นอีกเรื่องหนึ่ง** review แบบ blameless ตั้งอยู่บนสมมติฐานว่าคนพยายามทำสิ่งที่ถูก การก่อวินาศกรรมหรือการกระทำที่มุ่งร้ายเป็นเรื่องของ process อีกตัว (security, HR) และเกิดขึ้นน้อย *Just Culture: Restoring Trust and Accountability in Your Organization* ของ Dekker (ฉบับที่ 3, 2016) อธิบายสองวิธีในการให้คนรับผิดชอบหลัง incident: แบบ retributive ที่ถามว่ากฎข้อไหนถูกละเมิด โดยใคร และผลที่ตามมาควรเป็นอะไร และแบบ restorative ที่ถามว่าใครเจ็บ เขาต้องการอะไร และเป็นหน้าที่ของใครที่จะตอบสนองความต้องการนั้น บ่อยครั้งก็ด้วยความช่วยเหลือจากคนที่เกี่ยวข้อง
- **ความล้มเหลวจาก third party** อย่าง incident ของ payment provider เองในที่นี้ ก็ยังควรมี postmortem ฝั่งเรา: ระบบของเราทำตัวยังไงตอน dependency แย่ลง และอะไรที่เราคุมได้

มันต้นทุนมากกว่าที่ได้คืน ถ้าบังคับทำ postmortem เต็มรูปแบบกับทุก alert เล็ก ๆ: การเขียนจะกินเวลาที่มันควรจะช่วยประหยัด ตั้ง trigger ไว้ และใช้ format ที่เบากว่าสำหรับเรื่องที่ต่ำกว่านั้น ส่วน process ที่ไม่ได้กันเวลาไว้ให้ action item จะได้แค่ document ไม่ได้การปรับปรุง

## กับดักที่เจอบ่อย

- **เข้าใจว่า blameless คือไม่มีผลตามมา** ความรับผิดชอบเปลี่ยนรูป ไม่ได้หายไป: คนต้องรับผิดชอบในการเล่าเรื่องให้ครบและในงานที่ต้องตามต่อ (Tom เป็นเจ้าของการแก้ timeout) ไม่ใช่รับผิดชอบด้วยการถูกลงโทษ พูดเรื่องนี้ออกมาดัง ๆ ใน review เพราะทั้ง manager และวิศวกรก็เข้าใจเรื่องนี้ผิดกัน
- **ระบุ human error เป็น root cause** มันหยุดการสืบหาตรงจุดที่ควรเริ่มพอดี ถามว่าอะไรทำให้ความผิดพลาดเกิดได้และเกิดง่าย (default ที่เปลี่ยนเงียบ ๆ, check ที่ดู signal ผิดตัว) แล้วแก้ตรงนั้น
- **ตามหา root cause ตัวเดียว** incident ในระบบที่ซับซ้อนมักต้องมีหลายเงื่อนไขเกิดพร้อมกัน ของ Acme มีสี่ข้อ และการแก้ข้อใดข้อหนึ่งก็ยังทิ้งอีกสามข้อไว้ที่เดิม ให้ลิสต์ contributing factor และจัดการตัวที่สำคัญที่สุด การทำ five whys ช่วยกระตุ้นความคิดได้ดี แต่ why สายเดียวมักไปหยุดที่สาเหตุเดียว เลยให้ถามว่า *มีอะไรอีก* ในทุกขั้น
- **action item ที่ไม่เคยถูกปิด** action ที่ไม่มีเจ้าของ ไม่มีวันที่ หรือไม่มี priority ทำให้ postmortem กลายเป็นแค่ document ไม่ใช่การปรับปรุง ให้แต่ละข้อมีเจ้าของหนึ่งคน วันครบกำหนด และ ticket ใน backlog ของทีม คอย review ข้อที่ยังเปิดอยู่เป็นประจำ และถือว่า incident ที่เกิดซ้ำคือสัญญาณว่าการตามงานต่อล้มเหลว
- **ทำ postmortem แค่กับ outage ใหญ่** near miss (alert ที่ไม่กระทบลูกค้า, deploy ที่ rollback ทัน) แสดงจุดอ่อนแบบเดียวกันโดยเจ็บน้อยกว่ามาก ใช้ format สั้น ๆ และตั้งเกณฑ์ไว้ต่ำ
- **template ที่กรอกโดยไม่ได้คุยกัน** form ที่คนคนเดียวกรอกหลังเหตุการณ์ บันทึกว่าเกิดอะไรขึ้น แต่ไม่ค่อยบอกว่าทำไมมันถึงดูสมเหตุสมผลสำหรับคนที่เกี่ยวข้อง จัด review กับทุกคนที่มีส่วนร่วม โดยมี facilitator และเขียนจากการคุยนั้น
- **ภาษาที่โทษคนคืบกลับมา** "ควรจะ", "ไม่ได้ทำ" และ "สะเพร่า" แทรกเข้ามาได้แม้จะตั้งใจดี อ่าน draft หาคำพวกนี้ก่อน review แล้วเขียนใหม่ในแง่ของสิ่งที่คนรู้และเห็น
- **เก็บเข้าลิ้นชัก** postmortem ที่ไม่มีใครอื่นอ่าน ปกป้องได้อย่างมากแค่ทีมเดียว แชร์ให้กว้าง ติด tag ให้ค้นเจอ และเปลี่ยนบทเรียนที่ซ้ำ ๆ ให้เป็นค่า default ที่ใช้ร่วมกัน อย่างที่ทีม platform ของ Acme ทำกับ timeout
- **เผยแพร่ช้า** ตัวอย่างฉบับแย่ใน workbook ออกมาสี่เดือนหลัง incident ตอนนั้นมันเกิดซ้ำไปแล้ว ตั้ง deadline และทำให้ได้ตามนั้น
